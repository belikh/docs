# Documentation with jupiter-docs

Write documentation once, as Markdown in `docs-src/`. The `jupiter-docs` command (package `@belikh/jupiter-docs`, source in `belikh/docs` at `packages/docs`; the site is docs.jupiter.au) generates three outputs from it, so they cannot drift:

| Output | Where | Command |
| --- | --- | --- |
| Static site (docs.jupiter.au) | `dist/site` | `jupiter-docs build --site` |
| Plain GitHub Markdown | `docs/*.md` | `jupiter-docs build --md` |
| PDF, one per project | `dist/<id>.pdf` | `jupiter-docs build --pdf` (a project's pages link to its own PDF; the site copies each one that exists) |

**Never edit `docs/*.md`, `dist/site` or the PDF by hand.** Every generated Markdown file starts with a `Generated by jupiter-docs` comment; change its source in `docs-src/` and rebuild. Hand-written files in `docs/` that lack that comment (specs, status, notes) are not part of the system and are never touched.

The visual rules (type, colour, space, graphics) are in `DESIGN.md` in the `jupiter-design-system` skill. The generator already applies them to the site and the PDF, so you write content and leave the look alone. Do not add CSS, colours or images of your own to a docs page. The Home Assistant install badges in the next section and your own `::diagram` drawings are the exceptions.

## Workflow

1. In `belikh/docs` run `npm run update:design` once; it downloads the latest design system release into `vendor/design`, which is not committed. A project that uses the generator elsewhere has its own copy of that step or sets `JUPITER_DESIGN_DIR`.
2. Edit or add a file in `docs-src/`. The file name is the page id (`guides/setup.md` is `guides/setup`).
3. `jupiter-docs check` validates the source and the wording, and names the file and line of every problem.
4. `jupiter-docs build` writes `docs/*.md` and `dist/site`. Commit `docs-src/` and the regenerated `docs/*.md` together. CI runs `jupiter-docs build --check` and fails when a generated file is stale.
5. `jupiter-docs build --pdf` builds one PDF per project: the hub's pages, then each imported project's. It needs `xelatex` and `rsvg-convert`. Build the PDFs before `build --site`, so that the site links them.
6. For a new project run `jupiter-docs init`, which creates `docs.config.json`, `docs-src/index.md` and a first page in the `start` folder. Then follow "Put a project on docs.jupiter.au" below.

## Put a project on docs.jupiter.au

docs.jupiter.au shows every project. A project's pages stay in the project's repository; `belikh/docs` holds no copy and imports them before each build (`jupiter-docs import`, daily and on every push there).

1. In the project's repository, write `docs.config.json` (`project`, `id`, `description`, an `icon`, `versionFrom`, `repo`, a `glossary` if the pages use terms) and the pages in `docs-src/`. Run `jupiter-docs check`, then commit both to the default branch.
2. A public repository of `belikh` is now registered: the `discover` key in `docs.config.json` of `belikh/docs` finds every such repository that has a `docs.config.json` at its root. Nothing is edited in `belikh/docs`.
3. A repository of another owner, or one that needs a fixed branch or another id, is registered by one entry in `sources` of `belikh/docs`: `{ "repo": "owner/name" }`, with optional `ref`, `id`, `title`, `summary` and `icon`.
4. The site reads the project's newest release, or its default branch when there is no release or the release has no `docs.config.json`. Pages appear at `/<project id>/<path of the file>/`. The id is `id` in the project's `docs.config.json`, or the repository name in lower case when it has none. Choose it once: a published address does not change.
5. To publish straight after a release, the project's release workflow sends a `repository_dispatch` event of type `docs-changed` to `belikh/docs`.

A project whose pages fail `jupiter-docs check` is left out of the site with a warning in the build log, so run the check in the project's own CI. Private repositories, forks and archived repositories are not discovered. `docs/adding-a-project.md` in `belikh/docs` is the full reference.

## Sections

A folder in `docs-src/` is a section; the page's `section` key is only needed for a page that is not in a folder. Use these five folder names in every project. They have a fixed title, summary, icon and order, so each project is laid out the same way:

| Folder | Title | What goes in it |
| --- | --- | --- |
| `start` | Start | Install and first run. Often one page. |
| `guides` | Guides | One task per page, as numbered steps with commands to copy. |
| `reference` | Reference | Every command, option, file format and API, in tables with defaults. |
| `concepts` | Concepts | How it works and why it is built this way. |
| `develop` | Develop | Build, test and release. |

Another folder name becomes a section titled after the folder. List `sections` in `docs.config.json` only when a project needs its own titles or order. When you add a feature, add or change its guide and its reference entry in the same commit, and put a new page in the folder that matches its kind before inventing a section.

## Source format

`docs.config.json` (project root) holds `project`, `description`, `icon` (shown on the project's card), `version` or `versionFrom`, `repo`, `siteUrl`, `base`, `sections` (optional, in navigation order, each `{ id, title, summary, icon }`), `glossary` (term to definition) `hero` (a spot graphic for the landing page) and `diagrams` (folders of SVG files for `::diagram`, default `diagrams`). A site that shows other projects also has `sources` and `discover`, and `redirects` (old address to page id) keeps an address alive after a page moves. Unknown keys are errors.

Each page starts with a YAML block:

| Key | Meaning |
| --- | --- |
| `title` | Required. The page title (the body starts at `##`). |
| `summary` | Required. One sentence; shown under the title, in search and on cards. |
| `section` | A section id. Default: the name of the page's first folder. Required on a page that is not in a folder, except `index.md`. |
| `order` | Number. Position in the section (default 100). |
| `icon` | A name from the icon tier of the graphics set, for example `home`. |
| `audience` | `users`, `developers`, `agents` or `maintainers`. |
| `status` | `draft`, `stable` or `deprecated`. |

Headings never skip a level. Raw HTML is an error: put literal `<tags>` in backticks.

## Directives

Block directives start with colons and end with a line of colons; use four colons for the outer block when nesting.

- `:::note`, `:::tip`, `:::warning`, `:::danger` with an optional title after the name: a callout.
- `:::see-also` containing a list of links: a "See also" block.
- `::graphic tier/name Alt text`: a graphic from `@belikh/jupiter-graphics`, for example `::graphic rule/end`. Alt text is optional; leave it out for decoration. Use a `rule` between major blocks and at most one `spot` or `scene` per page.
- `::diagram name Alt text`: a drawing that the project made itself, from `name.svg` in a diagram folder (`docs-src/diagrams` by default). Alt text is required. See "Add a diagram".
- `::glossary`: lists every glossary term (one page only).

Inline and link syntax:

- `[[page-id]]`, `[[page-id#anchor|link text]]`: a link to another page or heading. The id is the file's path without `.md`, and names a page of the same project first. On docs.jupiter.au, `[[design/consuming]]` links to a page of another project and `[[design]]` to its landing page. Relative links to `.md` files also resolve.
- `[[term:Name]]`: a glossary term that links to the glossary page. A project's own `glossary` is looked up first, then the site's.
- `[text](https://…)`: a link to any URL. A bare URL such as `https://github.com/owner/repo` in running text or a table cell is plain text and is not clickable. Always write the link as `[text](url)`.
- `[![alt text](image-url)](link-url)`: a clickable image, such as a badge. The image needs alt text. The generator checks that the image URL is absolute or a file that exists.
- Code fences take a language and an optional title: ` ```sh title="Install" `. Always give a language; use `text` for plain output.
- Tables are plain Markdown tables with no merged cells. Keep cells short; put long text below the table.

## Home Assistant install buttons

A page for a Home Assistant integration starts with the install buttons from my.home-assistant.io. A visitor selects one and Home Assistant opens the repository or the setup flow. Use these two forms, with the project's own owner, repository and domain:

- The HACS button on the install page, for an integration that HACS installs from a repository:

  ```md title="Install with HACS"
  [![Add to Home Assistant](https://my.home-assistant.io/badges/hacs_repository.svg)](https://my.home-assistant.io/redirect/hacs_repository/?owner=OWNER&repository=REPO&category=integration)
  ```

- The setup button on the page that adds the integration, with the `domain` from the integration's `manifest.json`:

  ```md title="Add integration"
  [![Add integration](https://my.home-assistant.io/badges/config_flow_start.svg)](https://my.home-assistant.io/redirect/config_flow_start/?domain=DOMAIN)
  ```

Put the button on its own line, followed by a blank line, and write the numbered steps after it. Check both URLs return 200 before you publish. `jupiter-docs` does not check them.

## What each output looks like

- Site: the app's look from the tokens and components CSS, with SGI fonts, in light and dark. The home page has a card per project, and each project has a landing page. Every page has a left navigation by section, an on-page contents, previous and next links and a print style. Search covers all projects, and `llms.txt` lists every page with its summary.
- `docs/*.md`: plain GitHub Markdown. Callouts become GitHub alerts, graphics and diagrams become light/dark `<picture>` blocks, page links become relative `.md` links.
- PDF: `jupiter-docs.cls` in `latex/` of `belikh/docs`, which extends `jupiter.sty` from the design system's LaTeX bundle, with a cover, running header, numbered sections and callout boxes.

## Add a diagram

Use a diagram for a figure that the graphics set does not have: a wiring plan, a timing chart, a state machine. Draw it as thin line art in an SVG file in `docs-src/diagrams/`, and place it with `::diagram name Alt text`. `jupiter-docs check` tests these rules:

- the `<svg>` has a `viewBox` at most 720 wide, `fill="none"`, `stroke="currentColor"` and one `stroke-width` between 1 and 3
- colours are `currentColor`, `none` or `var(--jp-NAME)` for `text`, `text-muted`, `border`, `accent`, `ok`, `warn`, `danger` or `info`; never a hex value and never opacity
- text sets no `font-family` (it is JetBrains Mono), and 13 or 14 units is readable in the PDF
- no fills, gradients, filters, images, scripts, `style` attributes or links to other files
- a marker's colour is set on the marker's own path

The site inlines the SVG in the theme colour, `docs/diagrams/` gets a light and a dark copy for the Markdown, and the PDF gets the light copy drawn with the design system's fonts. Commit the generated copies with the pages. See `docs-src/writing-documentation.md` for a worked example.

## Add a graphic

Graphics come only from `@belikh/jupiter-graphics`: no emoji, no other icon sets, no screenshots as decoration. If the set lacks what you need, add it to the graphics package of `belikh/design` first (see `jupiter-design-system`); after its next release use its `tier/name`. `jupiter-docs check` fails on an unknown name.

## What a good page has

- A title that names the task or the thing, and a summary that says in one sentence what the reader gets.
- The command or the result in the first screen. Steps are a numbered list, one action each, with the command to copy and the output it prints.
- Every option, flag, environment variable and file in a table with its default. Check each against the code before you write it down.
- One example that can be pasted and run as it is.
- The errors a reader will meet, quoted exactly, each with its cause and its fix.
- A `:::see-also` block with the next page a reader needs.
- `status: draft` until the steps have been run from a clean checkout.

## Voice

Read `VOICE.md` (beside this file) before you write any prose. It is the voice of every jupiter.au project, shared with the `github-readme` skill. In short:

- Answer first: the first sentence says what the thing is or what the reader gets.
- One idea per sentence, most under 25 words. Say "you", use the present tense, write steps as commands.
- State facts a reader can check: numbers, names, defaults, paths, exact error text. Delete a sentence that has none.
- Leave out praise words, sincerity words, signposting, contrast for effect, the em dash, emoji and exclamation marks. `VOICE.md` lists them with what to write in their place.
- The page does not describe itself, and it stops when the content ends.

`jupiter-docs check` enforces this on every page: a listed word or phrase is an error, a long sentence is a warning. Fix the sentence, and do not swap the word for a synonym. Headings are nouns or short verb phrases. When a command, path or option changes, change the page in the same commit.

## README files and release notes

A `README.rst`, a profile README, a repository description and release notes are written with the `github-readme` skill, which has its own layout and format. Use that skill for those files and this one for everything in `docs-src/`. Both follow `VOICE.md`. Check a README with `jupiter-docs voice README.rst`.

## Where things live

- `packages/docs`: the generator (`src/spec.mjs` lists every directive and header key; `src/cli.mjs` the commands).
- `docs-src` and `docs.config.json`: the site's source. `docs/writing-documentation.md` is the full format reference.
- `latex/jupiter-docs.cls`: the PDF class.
- `skill/VOICE.md`: the voice guide. `VOICE` in `packages/docs/src/spec.mjs` is the word list the check uses.
- `skill-readme/SKILL.md` in `belikh/docs`: the `github-readme` skill, for README files. `jupiter-docs init` links it and this skill into a project's `.claude/skills`.
- `scripts/update-design.mjs`: downloads the design system release.
- Pages of other projects are fetched by `jupiter-docs import` into `docs-src/_imported/<project id>/`, with the list of projects in `projects.json` beside them; the front matter key `source` marks them. Do not edit them in `belikh/docs`: change the file in its own repository.
